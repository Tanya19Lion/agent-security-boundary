# Межа довіри для агента, що читає зовнішній текст

Гіпотетичний приклад: агент підписаний на тікет-фід / event-queue зовнішньої
системи (баг-трекер, webhook, черга завдань) і за цими тікетами сам пропонує
або вносить зміни в репозиторій.

## 1. Звідки приходить чужий текст

- Зовнішня система (issue tracker, support-форма, webhook-подія, партнерський
  API) пише в event queue / ticket feed.
- Процес-споживач (worker) читає чергу і передає текст тікета як частину
  промпта моделі.
- **Увесь текст тікета — недовірений вхід.** Його writer — будь-хто, хто може
  створити тікет чи подію (клієнт, бот, у гіршому разі зловмисник, що
  скомпрометував зовнішню систему або просто має доступ створити issue).

## 2. Що має процес, який це читає

Worker, що виконує читання черги й виклик моделі, на практиці вже має (бо
без цього не може виконати свою роботу):

- **Секрети/ключі**: токен для API зовнішньої системи (щоб писати назад
  коментарі/статус), ключ LLM-провайдера, креденшели БД (якщо агент може
  дивитись дані для діагностики), можливо git-токен з правом push.
- **Право змінювати код і конфіг**: доступ на запис у робочу копію
  репозиторію, можливість запускати `npm install`, редагувати CI/CD конфіги.
- **Доступ до main**: якщо агенту дозволено створювати коміти/PR, а тим
  більше — мержити, то компрометація агента = компрометація main.

Це і є небезпечна комбінація: **недовірений вхід + реальні привілеї в одному
процесі**.

## 3. Межа довіри (trust boundary)

Межа — це точка, де чужий текст **вперше** потрапляє в процес, що вже тримає
секрети й права на запис. У типовій реалізації це момент, коли worker бере
сирий `ticket.body` і кладе його в промпт моделі, яка потім викликає tool'и
з тими самими правами, що й worker.

```
[зовнішня система] --(недовірений текст)--> [queue]
                                                │
                                   ← МЕЖА ДОВІРИ ТУТ →
                                                │
                                        [worker-процес]
                                  (має: LLM key, git token,
                                   API-токен зовнішньої системи,
                                   право писати в repo)
                                                │
                                           [LLM-агент]
                                                │
                                        [tool calls: fs, git, http]
```

Усе, що відбувається **до** цієї межі (парсинг JSON тікета, витяг полів),
повинно поводитися з текстом як з даними. Усе, що **після** межі
(інструкції моделі, вибір і виконання tool-викликів) — потенційно під
впливом зловмисного тексту, і саме тому вимагає окремих, незалежних від
моделі обмежень.

## 4. Архітектура захисту

### 4.1 Дешева перевірка до запуску моделі (`prefilter.ts`)

Регулярки/евристики, що не потребують виклику LLM:
- відомі фрази prompt injection ("ignore previous instructions",
  "you are now in developer mode", "reveal your system prompt" тощо);
- маски секретів у самому вхідному тексті (AWS-ключі, приватні ключі,
  інше — на випадок, якщо зловмисник намагається "підкинути" секрет,
  який потім агент "випадково" залогує чи відправить далі);
- команди shell/exfiltration (`rm -rf`, backticks, `curl ... | sh`,
  `$(...)`, base64-пейлоади);
- явні вимоги привілейованих дій текстом ("merge to main without review",
  "disable the firewall").

Якщо знайдено — **блок** (запит не йде в модель). Дешева перевірка не
намагається зрозуміти намір, лише відсікає явно небезпечні/очевидні
шаблони; вона не замінює обмеження рівня 4.2, лише знижує кількість
випадків, коли інжекція взагалі доходить до моделі.

### 4.2 Жорсткі обмеження після моделі (`policyGuard.ts`)

Незалежно від того, що "вирішила" модель, виконавчий шар:
- **не виходить у мережу** за межі явного allow-list (за замовчуванням —
  порожній, тобто все заборонено);
- **не чіпає захищені шляхи**: `.env*`, `.git/`, `node_modules`,
  CI-конфіги, секрети — read і write заборонені незалежно від того, що
  "попросила" модель;
- **не пише напряму в продукт/main**: будь-який запропонований agent'ом
  diff чи дія лягає в черзу `pendingReview` — застосовує її лише людина.
  Це головний бар'єр: навіть якщо prefilter і сама модель помилилися,
  шкода обмежена "запропонованою дією", яку ніхто не підтвердив.

### 4.3 Розподіл ролей

Модель **пропонує**, окремий код із жорстко прописаними правилами
**дозволяє або блокує**, людина **схвалює**. Жодна з цих трьох ролей не
довіряє результату попередньої без перевірки.

## 5. Що саме тестуємо

- Один відомий шкідливий вхід (`MALICIOUS_TICKET` у `guardrail.test.ts`) —
  поєднує prompt injection + спробу дістати секрет + команду ексфільтрації +
  вимогу мержити в main без ревʼю. Очікування: `prefilter` повертає
  `verdict: "block"`.
- Один безпечний вхід (`SAFE_TICKET`) — звичайний баг-репорт. Очікування:
  `verdict: "pass"`, текст не змінюється.

Тест — регресійний страховочний пояс: будь-яка майбутня зміна `prefilter.ts`,
що випадково послабить правило, зламає цей тест.
